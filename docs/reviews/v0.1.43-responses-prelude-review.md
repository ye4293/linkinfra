## 修改内容

| 文件 | 修改与目的 |
| --- | --- |
| [relay/controller/opeai_response.go](../../relay/controller/opeai_response.go) | 每次上游尝试独立缓冲 `response.created`、`response.in_progress`、`response.queued`，最多 32 个事件、1 MiB 原始 JSON；前置阶段失败时不输出缓冲内容，允许外层处理真实错误状态及重试 |
| [relay/helper/stream_scanner.go](../../relay/helper/stream_scanner.go) | 对启用延迟策略的流，在下游尚未提交时跳过 ping；判定与流写入使用同一把锁 |
| [relay/util/relay_meta.go](../../relay/util/relay_meta.go) | 新增 `DeferPingUntilResponse`，由原生 Responses 流处理器设置，其他协议默认不启用 |
| [controller/retry_policy.go](../../controller/retry_policy.go) | 重试判定首先检查客户端 context，已取消则返回 `client_cancelled` |
| 现有 Responses 测试文件 | 扩展换渠、事件顺序、缓冲边界、状态缓存及取消回归；将模拟“已输出”的旧前置事件夹具改为 `response.output_item.added` |

首个非前置事件到达后，先记录所有待发送事件携带的状态，再按原顺序发送原始 JSON。这样保留响应 ID、扩展字段和大整数，不经 DTO 重编码。发生流内 429 的失败尝试，其尚未输出的前置事件与响应 ID 不会混入下一次尝试。

缓冲超限返回 `responses_prelude_limit_exceeded`（502），不会以强制发送前置事件的方式解除上限。额度是原始前置 JSON 的上限，不代表整个请求或扫描器的总内存上限。

## 代码审查结果

| 审查项 | 结果 |
| --- | --- |
| OpenAI / Azure 是否共用修复 | 两种渠道最终调用同一个原生 Responses 流处理器；Azure 的路径和参数由适配器处理，未另设遗漏的流错误分支 |
| 错误识别与提交顺序 | 流内错误识别发生在缓冲/发送及状态记录之前；前置阶段的失败不会提交 HTTP 200 |
| 重试隔离 | 缓冲为函数局部状态，每次尝试重新创建；外层继续使用原有请求正文重放与失败渠道排除机制 |
| provider 与会话边界 | 继续经过原有 provider 过滤；`previous_response_id` 等资源绑定仍限制原渠道。配置了 provider 边界时，耗尽后不会跨 provider 回退 |
| 状态记录失败 | 仍设置 `responses_state_record_failed` 阻止重试；输出前不暴露未记录的响应 ID，输出后用规范失败事件收尾 |
| 已输出后失败 | 保留 `Writer.Written()` 保护，不拼接另一条上游响应；继续兼容数字错误码、空错误和终止失败事件 |
| ping | 前置阶段跳过，开始输出后恢复已有 ping 行为；相关成功与失败场景均有覆盖 |
| 客户端取消 | 在重试判定时停止；前置缓冲期间与已输出期间的取消用例均只调用一次上游 |
| 计费与日志 | 失败路径不进入成功结算；路由测试验证换渠成功只有一条消费日志，用户和令牌只扣一次额度，全失败则零扣费 |
| 测试有效性 | 使用本地真实 HTTP 服务及完整网关路由，验证实际上游调用次数、请求正文、响应字节、额度和状态来源，不只断言内部变量 |

边界说明：同 provider 限制依赖既有 provider 配置及请求绑定，不是单凭“渠道类型为 Azure”推断。未配置 provider 的旧回退策略没有在此次修改中重写。

## 生产日志验收方法

按同一个 `request_id` 筛选 `responses_retry_diag`，核对：

1. `request_started` 中 `version="v0.1.43"`。
2. 上游返回 HTTP 200，随后 `upstream_sse_error` 中 `error_status=429`。
3. `decision` 中 `response_written=false action=retry`。
4. `channel_selected attempt=2`（或后续序号），渠道 ID 改变，provider 符合原请求边界。
5. 最终成功出现 `request_succeeded attempts=2` 或更多；即使备用渠道也失败，第 4 步仍能证明实际进入换渠尝试，需结合后续 `upstream_headers` 确认新渠道返回了响应。

只有“429”和不同请求 ID 的成功日志，不能证明同一次网关请求进行了自动重试。

以下停止原因应结合请求状态判断，不应直接判为修复失效：`response_already_started`、`client_cancelled`、`response_state_record_failed`、`specific_channel_requested`、`provider_channels_exhausted`、`response_state_channel_exhausted`、`retry_limit_reached`。`text_deltas=0` 也不代表尚未输出，例如已发送 `response.output_item.added` 时仍不能重放。
