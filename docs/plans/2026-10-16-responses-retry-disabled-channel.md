# Responses 禁用渠道与重试诊断修复

## 背景与目标
用户报告禁用渠道仍被命中，Responses 429 后只有一次失败记录。期望保留单请求聚合日志，并完整记录各次真实尝试。

## 方案设计
- response ID 缓存和规则亲和只保存渠道偏好，选用时从数据库读取当前渠道配置与状态。
- Responses 重试选渠失败后不再使用保存的旧渠道对象兜底；正常选渠自身已支持耗尽后循环。
- 在最后一次 retryHistory 中保存停止原因，区分流已输出、状态存储失败、错误不可重试、渠道边界无候选和次数耗尽。
- 全量回归捕获 StreamScannerHandler 的完成信号被 ping 协程消费，导致主请求等待超时；增加独立 scannerDone 广播，并在启动扫描协程前注册 WaitGroup。
- 完整路由回归覆盖 HTTP 429 跨渠道失败、首事件 429、旧缓存中的禁用渠道和重试期间禁用渠道。
- 发布复审：失效亲和同时清除旧 key 索引和禁止重试标记；ping 的 WaitGroup 在退出清理完成后才释放。
- 大正文完整路由回归覆盖流式/非流式 429 后成功，校验正文完整重放、两条尝试明细和仅成功一次扣费。

## 影响范围
不更改数据库结构、聚合日志展示约定或历史状态/provider 兼容边界。用户已授权排查修复，按第二张截图澄清保留聚合日志。

## 验证方式
运行相关包测试、全量编译与静态检查；核对实际上游请求次数、retryHistory 渠道/状态、失败零扣费。
