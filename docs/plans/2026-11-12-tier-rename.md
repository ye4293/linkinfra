# 等级体系改名计划

日期：2026-11-12；分支：`worktree-tier-rename`。

## 背景与目标

将全新部署的默认等级从 Lv1–Lv6 改为 Start / Build / Scale / Enterprise，累计真实充值门槛分别为 $0 / $50 / $300 / $1000。保持自动升档、只升不降。先发布兼容代码，再由用户审核副本演练报告并手动提交迁移；本任务不连接生产库、不发布、不提交 Git。

## 方案设计

1. 核对本地 GORM 创建回调、默认值与 PostgreSQL 迁移源码。保留 `User.Group` 的原 tag，避免这次发布引入 users 列变更；通过使用创建事务的钩子填默认入门档，排序为门槛、sort_order、id。空表或查询失败回退 Start。
2. Flux 兜底使用数据入门档；文件容量按门槛分界 $5 / $50 / $100 / $250 分配；分组接口按配置顺序返回内存倍率的同一组 key。新库默认四档按业务顺序初始化。更新预览列宽和示例。
3. PostgreSQL 迁移和回滚均用单事务、有锁等待和语句超时、默认演练回滚。映射和四档定义位于顶部可编辑参数。迁移前验证混合 key、参数、渠道长度，保存带日期的快照；更新 users、channels、abilities、group_configs、GroupRatio，断言人数、集合、门槛与 key 完整性，输出前后报告。
4. 用户已确认按等级名合并、不降级：Lv1→Start、Lv2/Lv3→Build、Lv4/Lv5→Scale、Lv6→Enterprise。报告列出每个旧等级人数与充值未达目标门槛人数。折扣优先继承实际 GroupRatio，再取配置，再取 1；返现继承指定配置，默认取合并组中较高的旧等级。自定义分组和历史返现/日志保留。
5. 用户已确认 Enterprise 拥有 Scale 的全部渠道。顶部 inherits 参数默认 Scale→Enterprise，校验端点后对渠道和 abilities 同步补齐；列表在 from 后插入缺少的 to，完成继承后检查长度。多个关系按参数顺序反复应用直到稳定，abilities 使用相同的传递闭包，保证每条关系的包含断言成立。
6. 回滚恢复流量后的正常变化：未改组用户恢复快照，新注册/已改组用户按可配置反向映射恢复旧组，自定义组不动；恢复旧 abilities 时使用当前对应新行的 enabled/priority。四档配置变更先报告再恢复，自定义倍率保留当前值。渠道或 ability 结构变化、四档缺失、旧 key 或原 ID 冲突才中止。快照保留。

## 影响范围

- 代码：common/group-ratio.go、model/group_config.go、model/user.go、model/user_level_preview.go、controller/fileGo.go、controller/group.go、relay/channel/flux/adaptor.go 及相关测试。
- 新增两个迁移 SQL、上线手册、PGlite 验证脚本；更新 CHANGELOG。
- 正常旧库在迁移前继续使用旧等级与倍率。发布前必须检查 options.GroupRatio：缺失时人工写入旧版本当前实际生效的六档倍率（默认全部为 1），不能用可能不一致的 group_configs.discount 推断计费值。
- 文件容量有两项明确的兼容性调整：Lv6 从一律拒绝改为 2GB；未知分组从一律拒绝改为 100MB。默认旧门槛下 Lv1–Lv5 上限不变。门槛被改过的库，旧等级的上限会按各自的门槛重新分档；发布代码后、迁移前可能变大，这一行为已被用户接受。
- 不加宽 channels.group；映射后超 32 字符的渠道须先人工处理。迁移建议短暂停掉全部后端实例；在线迁移存在 RecalcUserLevel 读写窗口，提交后须复查和修正旧 key。
- 提交后删除 Redis user_group:* 并重启全部实例，避免最长 SYNC_FREQUENCY 内旧缓存导致无可用渠道。最终折扣与返现由用户在后台配置。

## 验证方式

- Go：入门档排序与回退、旧/新配置的创建默认值、显式分组、单连接事务、容量全部分界、分组顺序、四档初始化。依次执行 `go build ./...`、`go vet ./...`、`go test ./...`，使用指定 GOTMPDIR/TMP/TEMP、离线依赖。
- PGlite：虚构六档数据、不同渠道列表、自定义分组、ability 合并、倍率存在/缺失/不一致，验证演练无变更、提交断言、幂等、混合 key 和超长中止、回滚一致及用户后续升档保护。仅使用本地已安装包。
- 静态检查 SQL 禁令、差异、历史表未修改、快照列名约束。实际结果完成后记录于 CHANGELOG 和上线手册。

## 实施补充

- 已核对 GORM 1.25.7 与 PostgreSQL 驱动 1.5.7 源码。入门档查询使用原连接/事务；嵌套事务保存点使查询失败不会破坏 PostgreSQL 创建事务。
- 为避免演练消耗不可回滚的序列，配置迁移在事务内先删旧行，再复用继承源 ID 插入新行；继承源缺失时使用小于已有最小 ID 的负数。其余改写顺序沿用原方案。
- 默认继承若导致任一旧组倍率上升则中止，须审核并填写显式覆盖值。较高等级不保证实际倍率更低。
- 第二轮按审查意见调整回滚，允许注册、升档、自动启停和重新配置折扣返现；只有结构和恢复目标冲突中止。反向映射默认 Start→Lv1、Build→Lv2、Scale→Lv4、Enterprise→Lv6。
- 验证范围增加上线手册的全部 SQL，包括并发旧 key 修正、充值/保留档位取较高者；`CLAUDE.md` 记录序列演练与 PGlite NOTICE 回调的经验。

## 第一轮验证结果

- 针对性 Go 测试通过；关闭构建 VCS 信息嵌入后 `go build ./...`、`go vet ./...`、`go test ./...` 全部通过。首次未关闭时因沙箱环境读取 VCS 状态失败退出，未改业务代码规避。
- PGlite 最终 22 个场景通过，捕获 711 条 NOTICE；包括倍率存在/缺失及不一致、两种 quota 单位、演练无任何数据/目录/序列变化、完整提交与回滚、幂等、混合 key、超长、回滚冲突、手册核对与旧 key 修正。
- SQL 禁令、运行路径旧 key 扫描及差异空白检查通过。没有连接生产库或 Redis，没有验证真实多实例竞态、生产锁等待或 PostgreSQL 实例上的 GORM AutoMigrate；映射已确认，执行时机仍由用户审核副本演练后决定。

## 第二轮实施与验证计划

- 两份 SQL 保留 BEGIN、SET LOCAL、单个 DO、默认 ROLLBACK 和 SHARE ROW EXCLUSIVE 锁，在 DO 开头拒绝只读节点；整份文件可以作为客户端的一次请求发送。
- 报告渠道按原列表/新列表汇总，列启用数与最多 5 个示例；abilities 每个新档汇总；回滚用户最多列 50 个并报告总数，结构冲突最多列 20 个渠道 ID，不报告用户名或邮箱。
- 预览列宽按实际字符串最大字符数计算，补不同长度及 Unicode 用例。
- PGlite 保留原迁移基础验证，新增继承开关/参数/集合/长度、汇总报告上限、恢复流量后的回滚、反向映射校验和结构冲突。使用虚构数据构造批量渠道场景，不把生产具体数字写入仓库。
- 重跑 Go build/vet 和相关测试、PGlite 全部场景；完成后更新本计划、手册和 CHANGELOG 的第二轮结果。

## 第二轮验证结果

- PGlite 最终 40 个场景全部通过，包含本手册全部 SQL；虚构批量渠道场景的迁移报告为 29 条 NOTICE，用户/渠道 ID 截断检查通过。报告只含统计、配置和必要 ID，没有用户名/邮箱。运行中更新手册后重启验证，使用最终 SQL 完成检查。
