# 按来源拆分的模型监控 V2 设计草案

状态：用户已于 2026-09-22 授权重写，已按上游尝试口径实施；未执行生产 DDL。实际发布预算、方案取舍与验证范围见 `docs/source-metrics-v2.md`，本文件保留原始设计依据。

## 1. 已确认的需求与建议边界

- 生产数据库为 PostgreSQL，后端会自动扩容，请求量尚不确定。
- 监控与模型广场使用同一来源规则：配置的 provider 优先，空值回退渠道类型；同模型同来源的多个渠道合并，不同来源完全隔离。
- 支持 1H、24H、7D、30D。1～30 天是查询范围，不要求读取或长期保存所有原始日志。
- 对齐现有 rankings 的后台租约、进度保护、短事务与快照发布方式，不与其共用统计结果或抢占同一任务租约。
- 本版建议重写监控聚合、缓存与展示链路，继续利用现有持久化日志。暂不引入 Kafka、ClickHouse、每次上游调用额外写一张事件表，避免流量未知时增加运行组件与同步写入。
- 目标是有预算、有退让、可观测的数据库开销；不能仅靠建立索引承诺任意请求量下数据库绝对稳定。上线前必须完成 PG 执行计划与并发压测。

## 3. 统计身份与历史规则

统一 `SourceIdentity`，由目录和监控共同调用：

1. `source_key` 为 trim + 大小写归一后的配置 provider；未配置则取渠道类型对应的规范来源名再归一化。
2. `source_label` 为显示文本，已知来源保留 OpenAI、Azure、AWS 等规范拼写。不得用前端标签参与统计分组。
3. 未知渠道类型使用带编号的稳定标识，不全部归入 Other。
4. 模型采用用户请求/目录中的原始 model_name，保持版本差异；映射后的部署名可作诊断信息，不用于把同一公开模型拆散。
5. 每次选定渠道开始上游尝试时冻结来源快照，成功和失败、流式和非流式都从不可变 context/meta 写入；不在日志 goroutine 内再查渠道。最终来源另保留给客户端请求结果。
6. 渠道 provider 改名后，新请求进入新来源；旧曲线继续属于旧来源。删掉或禁用渠道不能抹掉已形成的历史统计。

新增日志字段建议：`metrics_source_key varchar(200)`、`metrics_version smallint`、`metrics_outcome smallint`、`metrics_duration_ms bigint`；推荐采用每次上游尝试口径时，再加 `metrics_attempts jsonb` 保存有界结构化尝试数组。前四个字段描述最终结果；attempt 数组保存各次 source_key、channel_id、attempt_no、结束时间、结果、耗时、TTFT、token 与采集版本，不包含正文/错误原文/渠道密钥。字段初期可空、不批量更新全表、不新增逐请求查询。正式实施前逐协议审计单位和计时起止。

attempt 数组与现有最终日志同一次 INSERT 持久化；不再解析包含自由文本的 other，也不每次重试额外同步插入一行。数组受服务端最大尝试次数和字节预算约束，溢出标 coverage 不完整并告警，禁止静默截断后仍标完整。该方式只能在请求最终完成落库后观察中间尝试，进程终止前未落库的尝试仍可能丢失；若要即时和零丢失，需要独立持久化事件路径。

不复用或重定义 logs.provider：该字段目前也服务 rankings 的既有语义。不修改状态兼容组 `ChannelProvider` 的路由规则，类型回退只用于公开目录及监控身份。

### 历史兼容

- V2 默认从所有新节点完成升级后的第一个完整 5 分钟桶开始。升级前的来源不完整数据不强行拆到当前 provider。
- 旧曲线可暂留“旧版全来源汇总”只读入口，与 V2 区分版本和覆盖范围；不能当某个来源的数据回退。
- 不默认按渠道当前配置回填历史。需要回填时，只对具有可信来源快照、成功/失败口径和足够原始日志的区间运行限速任务，并标明 coverage。
- 超过源日志保留期不能准确重算；应拒绝任务并说明缺失，不把空查询写回成零。

## 4. 指标口径：先把分母定义清楚

**建议来源健康监控按“每次上游调用尝试”统计，另保留客户端最终结果请求量。** 这样才能比较来源质量。两种计数必须使用不同字段和标签，不与计费请求数混淆：

| 指标 | 定义 |
| --- | --- |
| 调用量 | 已持久化的上游尝试数，每次 attempt 归其实际来源；同一客户端请求重试会产生多次调用 |
| 最终请求量 | 客户端已完成请求数，一次至多计一次，归最终来源；单独显示，不作为来源尝试成功率的分母 |
| 成功率 | 完整上游响应成功尝试数 /（成功尝试数 + 平台或上游失败尝试数）；消费日志有扣费不自动当成功 |
| 取消/无效请求 | 单独计数；未选到来源的鉴权、参数错误不硬归到某个来源；客户取消不默认算上游故障 |
| 延迟 | 当前一次上游尝试开始到结束的耗时，成功样本与失败耗时分开保存；页面平均值与百分位使用同一成功样本集；客户端端到端耗时另记 |
| 输出速度 | 首期明确为 completion_tokens / 当前成功尝试耗时的有效文本样本均值；不冒充纯生成阶段 TPS |
| TTFT | 有有效首 token 时间的流式样本均值，独立计数；非流式缺失不补 0 |
| P50/P95/P99 | 合并持久化直方图后估算，不平均各桶百分位，不使用本机进程样本 |
| RPM/TPM | 选定窗口的总请求/token 除以覆盖分钟数；部分覆盖标注不完整，不冒充完整窗口 |
| 无流量 | 请求数 0，成功率/延迟/速度为 null，状态 no_data；曲线断开，不能画成失败或零延迟 |

跨来源重试 A 失败、B 最终成功：A 调用量+1、失败+1；B 调用量+1、成功+1，最终请求量只给 B +1。同来源重试两次也计两次调用；页面将 RPM 标明为上游调用频率。token 不把最终日志总量重复分摊到所有 attempt，只计该次实际观察到的用量；缺失用量标 unknown，而非杜撰为 0。客户端取消单列。

若用户选择兼容旧版最终结果口径，可不采集 attempts、只用上述标量字段，改动较小；但必须标明“最终请求成功率（含重试）”，不能称其为来源每次调用的可用性。本草案其余持久化和后台架构兼容两种口径，正式开发前锁定选择。

首期覆盖同步文本/流式请求；图片、视频任务的“提交成功”与“生成成功”需单独口径。没有可靠完成事件的模型显示不支持该指标，而非伪造同等含义的健康率。

## 5. 推荐链路

```mermaid
flowchart LR
  A[每次尝试冻结来源与结果] --> B[请求结束时随现有日志持久化]
  B --> C[PG 单租约 worker：有界扫描 5 分钟桶]
  C --> D[5 分钟 / 小时 / 日汇总与持久化直方图]
  D --> E[按模型和来源生成版本化快照]
  E --> F[各实例有界内存缓存；可选 Redis]
  F --> G[模型列表、详情、四档曲线]
```

页面请求禁止查 logs，禁止因缓存过期直接触发历史 GROUP BY。日志量增长主要影响后台完成时间；访客增加主要影响快照读取与缓存命中率。

### 5.1 聚合任务与多实例互斥

- PG `metrics_v2_state` 保存 owner、lease_until、generation、heartbeat、coverage_start、dirty 状态、连续 finalized 水位和 log_purged_before。
- 采用数据库时钟进行租约判断；建议租约 60 秒、15 秒续租，具体值压测后确定。抢锁、提交、发布必须检查 owner + generation + 未过期，防止旧 worker 恢复后覆盖新结果。
- 未抢到租约的实例只服务快照；带随机抖动和退避竞争，不并行扫日志。不依赖“某台机器恰好是 master”维持唯一聚合者。
- 首期全库聚合并发固定为 1，不随服务副本数增加；资源预算不足时返回旧数据并标记 stale，不启动更多 worker 抢数据库。
- 不用 MAX(hour_timestamp) 猜进度；每个桶有任务状态，空桶也要标记完成，失败桶不会被跳过。

### 5.2 有界扫描、断点与幂等

- 固定 UTC 5 分钟区间 `[start, end)`，先处理已经结束并经过迟到宽限的桶，默认宽限建议 120 秒。首期可见延迟约 2～7 分钟加排队延迟，不能承诺实时。
- 日志读取只选统计所需列及有界 metrics_attempts，不读取 content、other、用户名、密钥或请求正文。以 `(created_at, id)` keyset 分页，每页初始 2000 行并限制字节预算；不用 OFFSET，不将时间直接推断为全局 ID 范围。桶归属采用最终日志落库记录时间，attempt 的真实完成时间保留作诊断；这是延迟可见的观测窗口，不宣称按实际尝试完成时刻实时落桶。
- 页游标只用于一轮固定区间扫描，绝不把自增 ID 当作提交顺序保证。较早 ID 的事务晚提交、异步日志迟到由区间复核处理。
- `metrics_v2_jobs` 保存每个区间本轮 generation、页游标、状态、最后错误、重试时间和 active_generation；`metrics_v2_stage` 保存当前轮的中间和/计数/直方图。
- 每页的中间汇总与页游标在同一短事务写入，失败整体回滚；重试不得再次累加已提交的同一页。进程重启从持久化断点继续，不清空后无限重扫。
- 扫描完毕后将完整结果写成新 generation；写入可分批，最后原子切换该桶 active_generation。未完成版本绝不进入快照，旧版本在新版本发布后由小批清理回收。worker 租约 generation 与桶数据 generation 分开，接管者可以继续已提交的页断点，但旧 owner 不能再写。
- 桶复核产生新版本时，同事务标记对应小时、日和来源快照为 dirty；下游汇总记录输入版本，发布前校验未变化。快照构建读取同一组已发布桶版本，不拼接新旧不一致的日/小时数据。发布失败保留 dirty 后重试，不能只修正细粒度数据却让 30 天曲线永久过期。
- channel 级和来源级由同一批中间样本生成，引用同一桶版本；不得一边成功发布、一边失败仍声称统计完整。公开统计只读来源汇总，避免把渠道行再次计入。
- 不在大事务内扫描日志或重建整天；读页、写页、发布分别受超时限制。
- 每轮最多执行 30 秒后台工作，单页查询初始 statement_timeout=3s、lock_timeout=500ms；页间暂停 50～100ms。超时降批量，连续失败指数退避，不无限立即重试。
- 存量规模未知时设置每轮最大行数、活跃任务数与中间数据预算；达到上限续跑并暴露 lag，而不是突破预算。

### 5.3 迟到、跨小时与恢复

- 当前未完成桶不伪装为完整点；跨小时继续封存上一小时最后的 5 分钟。
- 最近 1 小时内已发布桶进行一次延后复核；每个 UTC 日在次日按预算进行一次最终复核，完成后推进连续 finalized 水位。历史复核与新桶处理按配额轮换，不能饿死任一队列。
- 每个原始日志区间正常读取约 2～3 轮，而非每个节点每 5 分钟重读整个小时；小时/日汇总只从 5 分钟数据滚动生成，不再扫描 logs。
- 超出自动复核窗口的迟到数据不保证自动补齐；需在源日志尚存时定向重建。来源不可恢复、日志已清理时明确拒绝。
- “没有请求”与“日志写入失败、采集被关闭或节点版本混用”必须分别记录 coverage。自动扩容的新节点必须使用同版本采集；发生缺口则标 partial/stale，不显示正常健康率。
- 日志写入仍沿用已有路径，本方案不声称弥补尚未落库时进程崩溃的日志丢失。若需要零丢失的上游尝试审计，另行设计持久化事件队列。

## 6. 存储与索引（PG 优先）

表均位于 LOG_DB；业务库与日志库分离时不跨库 JOIN 渠道表。

| 表 | 用途 |
| --- | --- |
| `metrics_v2_state` | 单租约、覆盖范围、全局水位及发布状态 |
| `metrics_v2_jobs` | 每个粒度/时间桶的断点、候选版本及已发布版本 |
| `metrics_v2_stage` | 有界扫描的中间累加，按任务版本隔离 |
| `metrics_v2_buckets` | 300/3600/86400 秒分辨率的来源汇总及渠道明细 |
| `metrics_v2_snapshots` | 每个 model/source 的四档曲线、摘要以及列表迷你摘要，含版本和截止时间 |

bucket 保存可相加的 counts/sums、各指标 sample_count、固定版本的直方图，来源级 channel_id=0、渠道级 >0。日期统一 UTC。均值在最终读取时计算，避免平均均值；直方图合并前验证 schema_version/边界一致。

建议直方图覆盖 50ms～30min 的对数级有限边界，再设溢出桶；溢出百分位返回下界和 capped 标识，不人为编造 60s 等上限。具体边界随实际长响应分布验证，数组用 PG 紧凑整数数组或版本化二进制编码，避免 JSON 反复解析和大量浮点列。

### 6.1 日志扫描索引

保留 `idx_logs_created_at` 与现有排名索引；首期评估新增一条窄部分索引，不默认加包含所有监控字段的宽覆盖索引：

```sql
-- 设计示意，不是本次执行的迁移脚本。字段准备后在事务外执行。
CREATE INDEX CONCURRENTLY idx_logs_metrics_v2_scan
ON logs (created_at, id)
WHERE type IN (2, 5) AND metrics_version = 2;
```

对应 SQL 使用固定 `type IN (2,5) AND metrics_version=2` 谓词，时间与页边界使用绑定参数；验证 generic/custom prepared plan 都能命中，不能只测一次 EXPLAIN。业务状态由 metrics_outcome 判断，type 仅限定日志类别。

此索引仍可能回表，但控制索引写放大。只有 PG 实测回表成为瓶颈时才考虑 INCLUDE；需同时测日志 INSERT 延迟、WAL、索引尺寸与 autovacuum，不能只看 SELECT 速度。

### 6.2 汇总与任务索引

| 索引/键建议 | 查询目的 |
| --- | --- |
| buckets 唯一 `(resolution, bucket_start, generation, model_name, source_key, channel_id)` | 幂等写入同一完整版本 |
| buckets `(model_name, source_key, resolution, bucket_start, generation) WHERE channel_id=0` | 来源曲线、快照生成；联接 jobs.active_generation 排除旧版 |
| buckets `(channel_id, model_name, source_key, resolution, bucket_start)`，仅在管理员查询计划需要时添加 | 受限渠道下钻 |
| buckets `(bucket_start, id)` | 按时间小批清理、回收旧版本 |
| jobs 唯一 `(resolution, bucket_start)` | 桶完整性及 active_generation 查询 |
| jobs `(next_run_at, resolution, bucket_start) WHERE state IN ('pending','retry')` | 有界调度，避免扫描所有历史 job |
| stage 唯一 `(job_id, generation, model_name, source_key, channel_id)` | 同一页事务内累加、断点恢复 |
| snapshots 唯一 `(model_name, source_key, schema_version)` | 精确来源快照；全列表使用保留键/单独 summary 快照 |

索引名称不等于索引定义一致；迁移需检查字段顺序、谓词、indisvalid/indisready。已有无效同名索引不能被 IF NOT EXISTS 误当完成，交由审核后的运维步骤处理。

## 7. 缓存、API 与前端

### 7.1 版本化快照

- 每个来源模型的四档曲线和对应摘要一起生成；数据与 version/as_of/window_start/window_end/coverage_start/partial/finalized_until 一起保存。
- 内存保留只读对象或预序列化 JSON，原子替换；后台失败保留最后成功快照。Redis 可作跨节点加速，但不是幂等或完整性的依据。
- 新实例先加载列表小快照，再按需加载来源快照；冷读最多查一条已生成的 snapshot 行，不触发 logs/聚合查询。设 singleflight、有界并发、LRU、负缓存、过期抖动；缓存未命中没有成品时返回 preparing。
- 后台每 30～60 秒只检查版本，未变化不下载大 JSON。按来源刷新，不每次序列化全站 30 天数据。
- public API 支持 ETag、短 max-age 和 stale-while-revalidate；管理员明细使用独立私有端点，不能随公共 CDN 缓存。
- 具体快照总大小与条目数加入压测。节点内存初始建议上限 128MiB；淘汰后允许窄快照读取，不允许无限增加常驻缓存。

### 7.2 API 合约

- 目录增加 `source_key`，显示继续使用 provider 标签。稳定条目身份为 `(model_name, source_key)`，不再随代表渠道 ID 变动。
- 新监控读取使用 `model_name + source_key + period`；列表摘要按相同复合身份返回，建议数组或两层 map，不用易碰撞的字符串拼接。
- 来源多于一个而请求没给来源：返回明确选择需求，绝不默默展示全来源统计。
- 旧 `channel_id` 详情链接仅作为兼容入口：通过缓存的目录映射解析来源，再读取该来源全部渠道的统计；不能把监控限定到展示价格的代表渠道。
- 旧 `model_name` 形式可在只有唯一来源时自动解析，多来源返回歧义状态。新旧前端采用显式 v2/schema_version，避免旧页面把新结构读错。
- 价格逻辑延续本轮已确认的代表渠道选择；监控聚合的是该来源全部渠道，两者范围在设计中明确，不暗示指定了实际调用路由。

### 7.3 时间窗口与显示

所有窗口均截止同一 `as_of`，使用 `[start,end)`，以最近已完成的 5 分钟边界作为尾端：

| 选择 | 曲线粒度 | 摘要统计 |
| --- | --- | --- |
| 1H | 12 个完整 5 分钟桶 | 同一完整 1 小时 |
| 24H | 小时桶，头尾不足整小时用 5 分钟桶补齐 | 精确同一 24 小时；不再多算一个小时 |
| 7D/30D | UTC 日桶，头尾用小时/5 分钟补齐 | 精确选定天数；首末图点带实际覆盖起止 |

合并时选取互不重叠的 5 分钟、小时、日桶，不能把同一请求在多个分辨率重复求和。按日显示滚动窗口时可能出现部分首尾日，必须显示边界，不能假称固定 7/30 个完整自然日。

顶部成功率、延迟、速度、RPM、百分位与曲线随 period 一起切换；“24h 请求量”卡片若保留，明确固定标签。来源切换取消旧 fetch/丢弃迟到响应，避免 A 的请求覆盖 B。

图表 null 断线、无请求显示暂无数据；去除监控延迟曲线的平滑插值伪峰，优先直线/阶梯。显示“当前来源全部渠道”“更新截止时间”“数据延迟/部分覆盖”。低样本健康状态为 insufficient_data，不将一条成功请求标为高置信健康。

## 8. 保留、清理与 rankings 协调

“查询 1～30 天”与“保留多少原始日志”分开配置。现有 rankings 日汇总保留 90 天、比较查询最多取 60 天，本方案对齐其清理保护理念：

| 数据 | 初始保留建议 |
| --- | --- |
| 5 分钟汇总 | 35 天，支持精确滚动边界和复核 |
| 小时汇总 | 35 天 |
| 日汇总 | 90 天，与 ranking_daily 对齐 |
| 原始 logs | 沿用管理员配置；若要重算完整近 30 天，应保留至少 35 天。短保留仍能查已完成汇总，但不能重算已清理区间 |
| stage/未发布版本 | 任务完成后限速清理；未完成任务不因 TTL 自动删断点 |
| jobs/覆盖元数据 | 足够覆盖汇总保留与清理水位，不使用空表猜测历史完整性 |

- 最终日志删除截止取 `min(用户要求, rankings连续finalized水位, metrics连续finalized水位)`。若某功能从未启用，不引入永久阻塞；启用后暂停不能跳过未完成区间。
- 删除与重建共享明确的维护锁/水位协议；固定按排名、监控顺序获取锁，或使用独立 PG 维护租约，禁止随机顺序造成死锁。每个重建/清理事务都验证 fencing。
- 延续排行榜每事务 500 行、单次最多 10000 行/5 秒的有界删除思路；使用已选主键与时间条件删除，不做无 WHERE 删除，不做大事务清空。
- 数据库外人工删日志仍可能破坏重算能力，检测到源数据缺口时标 partial/拒绝重建。
- 监控积压不能偷偷删掉未完成日志“恢复进度”。接近存储阈值时告警，允许管理员显式放弃某段覆盖、记录缺口后推进，而不是假装完整。
- 初期不改现有 logs 为分区表；未来按实测表规模单独设计分区和保留策略，避免一次重构同时搬迁日志库。

## 9. PostgreSQL 稳定性预算与容量验证

### 9.1 自动扩容连接预算

现有每池 1000 的默认值必须在部署配置中收敛。以 `DB可用连接 = max_connections - 运维预留 - 其他服务占用` 计算，不凭空设定生产值：

`最大副本数 × 每副本数据库池数 × MaxOpenConns + 后台任务连接 + 迁移连接 <= DB可用连接`

若业务库、日志库共用一个 PG 实例但用了两个独立池，必须计两份。配置自动扩容最大副本数；没有上限就无法承诺数据库连接稳定。建议使用 PgBouncer/云数据库连接池作为全局上限，transaction pooling 与 GORM/驱动 prepared statements 的兼容需要实测后配置，不能直接切换。

后台专用小连接预算（首期最多 1～2 个连接/实际 leader），不重新给每个副本开启大池。限制 SQL 超时、锁等待、idle-in-transaction；不要在持连接期间 sleep。

### 9.2 容量模型

设 S 为活跃“模型×来源”数，C 为活跃“模型×来源×渠道”数，假设全天每桶都有数据，来源与渠道都落表时：

- 5m 行上界约 `(S+C) × 288 × 35`；
- 小时行上界约 `(S+C) × 24 × 35`；
- 日行上界约 `(S+C) × 90`；
- 例如 S=100、C=300，仅 5m 活跃版本就约 403 万行，还要计算索引、直方图、暂存与旧版本开销。

因此不向存储写每个无流量桶的空行；缺失点由已完成 job 与覆盖元数据生成。管理员渠道级细粒度是否需要保留 35 天，可在测得 C 后缩短独立保留期，但不能影响来源级曲线。

### 9.3 验证矩阵及初始门槛

以下是待压测目标，不是已取得的结果：

- PG 代表性规模：100万、1000万日志，来源/渠道热点倾斜、同秒大量日志、长响应/高失败率；有资源时加更大表。
- 副本数 1/4/16，目录与曲线并发 100/500，混入持续日志 INSERT、排名任务与清理。
- `EXPLAIN (ANALYZE, BUFFERS)` 检查 5m 页扫描和来源快照生成；ANALYZE 后同时检查 generic/custom plans。不要只在空表断言索引存在。
- 目标：公共监控请求 0 次原始日志查询；任意副本数只有一个日志扫描者；单页受 3s timeout 限制，写入/发布事务受 2s 预算约束。
- 目标：监控启用后日志写入 p95 相比基线增加不超过 10%，无长时间阻塞；计入新增有界 JSON 的写入/TOAST/WAL 开销。超过则降低后台预算并检查 payload 大小，不能仅通过缓存掩盖新增采集成本，也不能通过加副本放大压力。
- 检查 PG connections/wait events、WAL量、dead tuples、autovacuum、索引尺寸、锁等待及复制延迟；共享资源已有余量不足时不进入全量启用。
- worker 暴露 lag_seconds、pending_buckets、scan_rows、query_duration、lease_failures、publish_failures、coverage_gaps；快照暴露 as_of 与 stale。

## 10. 必须通过的正确性与故障测试

1. 同模型 OpenAI/Azure、百度/DeepSeek、AWS/Anthropic 等数据完全隔离；同 provider 跨渠道/跨类型合并；大小写、空白、未知类型一致。
2. 改名、删渠道、代表价格渠道切换不重写历史；成功/失败来源快照都可匹配目录。
3. 3 个并发 writer 加 2 个竞争 worker，强杀 leader、租约过期、旧 leader 恢复，不能重复累加或覆盖新 generation。
4. 单页事务失败、最后发布失败、冷启动恢复、中间桶为空、任务中途重启，检查没有缺口和半版本可见。
5. 整点、午夜、UTC/本地时区、迟到事务先占 ID 后提交、最新桶回查、日志清理与重算并发。
6. 直方图重启与多实例一致，>60s、>30min、无 TTFT、零 token、部分流失败、扣费错误、客户端取消的分母和 null 合法。
7. 1H/24H/7D/30D 同范围的分子分母与直接校验结果相等；不同分辨率无重复；同小时多来源加权正确。
8. 缓存故障/Redis关闭/扩容冷启动/流量突增不会回退扫 logs；旧快照有截止时间，管理员数据不进入公共缓存。
9. 关闭日志、关闭监控、重新启用、混合版本节点分别标记覆盖；丢数据不被显示成 100% 或 0%。
10. PgBouncer 模式、索引无效、缺少表/列、数据量大的迁移场景与功能开关回退。

## 11. 实施拆分与上线顺序

### A. 冻结口径并完善采集

落实统一 source_key、每次 attempt 与最终请求 outcome/耗时快照，审计同步文本协议成功/失败、取消和重试路径，确保 attempt_no 唯一、最终日志只写一次。先不替换公开页面。产出单元测试和旧日志覆盖诊断。

### B. 新聚合与 PG 索引

增加 V2 表、任务租约、断点、持久化直方图、5m/小时/日汇总、定向重建和受保护清理。复用 rankings 已验证的思路，但不抽取大规模公共框架。完成真实 PG 故障与性能测试。

### C. API、快照与前端

新增显式 V2 合约及开关，更新目录身份、Mini、详情、图表、管理员下钻与代理参数；检查公共未登录访问和认证缓存隔离。加入 null/partial/stale 与周期一致性测试。

### D. 灰度与运维

1. 提供审核后的 PG DDL、索引验证和回退步骤；在 LOG_DB 上由单个迁移任务执行，不在自动扩容节点启动时建大索引。
2. 先部署兼容采集代码及小表结构；大表加列使用 lock_timeout、避开长事务，已有大表索引使用事务外 CREATE INDEX CONCURRENTLY。执行 DDL 前另行确认实际环境与锁窗口。
3. 确认所有节点新版本后设置 coverage_start，启用 V2 单 leader；限制旧 worker，避免长时间双倍扫描。保留旧成品快照作回退，不依赖持续旧聚合。
4. 开始积累，正常达到完整 1H/24H 后核对来源/总量/延迟，再切前端；7D/30D 显示实际覆盖，不必须等待30天才上线。
5. 观察数据库预算和 worker lag；异常只停 V2 计算并返回旧快照/stale，不影响业务转发。回退开关不删新表、不改计费、不清日志。

主要涉及：`common/model-provider.go`、`middleware/distributor.go`、relay meta/结算日志路径、`model/log.go`、`controller/retry_log.go`、新 `model/metrics_v2_*`、`model/main.go`/迁移入口、日志清理、`controller/model_metrics.go`、`controller/model_plaza.go`、router/config；前端 catalog、model-plaza 类型/列表/详情/图表、首页摘要、API代理及测试。
