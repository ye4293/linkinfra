# 百度千帆 V2 渠道升级

## 背景与目标

按用户要求，将现有百度渠道升级并命名为 `qianfanv2`，支持千帆 Chat Completions、Responses 和 Anthropic Messages 接口。

## 方案设计

- 保留渠道编号 15，更新默认地址为 `https://qianfan.baidubce.com`，渠道显示名称和适配器名称统一为 `qianfanv2`。
- 参考 MiniMax 的 OpenAI 兼容适配器：Chat 转发到 `/v2/chat/completions`，Responses 转发到 `/v2/responses`，Messages 转发到 `/anthropic/v1/messages`。
- 使用渠道 API Key；Chat/Responses 使用 Bearer，Messages 使用官方文档的 `x-api-key`，保留 Anthropic 版本与 beta 请求头。
- 处理根地址、`/v2` 和 `/anthropic` 地址配置；确保实际发起请求时使用千帆 URL 和鉴权覆盖方法。
- 同步后端渠道选项、默认模型和实际前端的渠道名称、地址及密钥提示。

## 影响范围

- 不新增渠道编号、不变更数据库结构。已有 15 号渠道需要使用新版千帆 API Key 和 V2 模型 ID；旧 AK|SK OAuth 凭据不再适用。
- 不在源码、测试、文档或提交中保存用户密钥。

## 验证方式

- 覆盖三种协议的 URL、鉴权、流式与非流式转发，以及渠道注册和模型列表。
- 用用户提供的密钥进行最小联调，记录接口返回及任何上游权限限制。
- 执行相关 Go 测试、`go build ./...`、`go vet ./...`，在隔离目录避开本地 `output/` 草稿；前端执行针对改动的检查。

## 使用方式与验证结果

- 渠道类型选择 `qianfanv2`（编号仍为 15），地址使用 `https://qianfan.baidubce.com`，密钥填写完整的千帆 API Key（`bce-v3/...`）。客户端继续请求本服务的 `/v1/chat/completions`、`/v1/responses` 或 `/v1/messages`。
- 后台渠道测试直接构造请求对象，没有原始 HTTP Body；适配器对此回退使用该对象，避免读取空 Body 引起崩溃。真实请求保留扩展参数、显式零值和模型映射。
- 真实上游验证：Chat 与 Messages 使用 `ernie-4.5-turbo-32k`，Responses 使用 `deepseek-v3.2`；三个接口的 JSON 与 SSE 请求均返回 HTTP 200，包含输出和结束事件。
- 模型支持范围因接口而异：当前密钥对 Responses 的 `ernie-4.5-turbo-32k` 和 `qwen3-14b` 返回 HTTP 401（模型不存在或无权访问），`deepseek-v3.2` 可用。适配器保留用户选择的模型，不自动替换。
- `go test ./relay/channel/baidu ./relay/channel/minimax ./relay/helper ./relay/controller ./controller` 通过；在隔离代码副本执行 `go build ./...` 与 `go vet ./...` 通过。SQLite C 依赖有既有编译警告。
- 实际前端 `../linkinfra-web` 已同步渠道名称、密钥格式和地址提示。两处改动的 ESLint 诊断与 HEAD 一致，没有新增问题；渠道表单原有 8 个 `react/no-unescaped-entities` 错误，因此定向 lint 命令仍返回失败。
- 模型发现 URL 和 Bearer 鉴权的本地测试通过；真实 `/v2/models` 请求返回 HTTP 429，本次未完成模型目录的线上验证。
- 密钥仅通过临时进程环境传入联调，不保存到源码、文档或测试文件。
