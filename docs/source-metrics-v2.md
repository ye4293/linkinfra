# 来源监控 V2：实现与上线说明

V2 将同名模型按目录 source_key 分开，同一来源的多个渠道合并。来源优先使用 config.provider，空值回退渠道类型，忽略大小写及首尾空格。请求发生时冻结来源，历史数据不随渠道改名变更。

## 统计口径

- 覆盖 OpenAI Chat/Completions、Responses、Anthropic 原生、Gemini 原生同步文本及流式调用。
- A 失败后重试 B 成功：A 失败一次，B 成功一次，最终请求量只给 B 一次。同来源重试也按多次调用统计。
- 页面请求量、成功率和 Calls/min 指上游尝试；`final_requests` 单独保留最终客户端请求量。取消单列，不算成功率分母。
- 延迟、百分位使用成功尝试的耗时；TTFT只使用有效流式样本；token只记实际有消费用量的最终尝试，不复制到失败重试。
- 百分位由持久化直方图计算，最大有限边界1800秒，溢出返回下界并标 capped。无样本返回null，低于20个成功/失败样本为insufficient_data。
- 尚未改造的异步图像/视频任务没有V2数据，不把提交成功当生成成功。

## 采集与持久化

每次尝试在relay调用外层记录来源、渠道、结果、耗时；请求结束后，将有界结构化尝试数组附到原有消费/错误日志，仍为一次日志INSERT。兼容异步结算先于或晚于relay返回；扣费失败不当成功，多条结算/错误记录只选一条携带监控样本。

最多64次尝试、32KiB payload、4条待写日志；超过预算记录显式不完整标记，worker报告错误并停止该桶，不发布截断的监控样本。使用独立metrics_model_name保存请求模型，不污染计费/排行榜字段。payload不含正文、错误原文或密钥。

这是基于已持久化日志的监控，不保证进程崩溃前未落库请求零丢失；中间重试在最终日志写入前不可见。桶时间使用日志created_at，因此不是实时完成事件流。混合新旧采集节点不保证完整覆盖，必须统一版本再开启。

## 后台预算

- PG数据库时间的60秒租约和generation fencing；每轮验证，只有一个worker扫描，扩容不会增加扫描者。
- 5分钟桶结束后等待120秒；每页100条、最大32KiB/条，keyset `(created_at,id)`。仅选模型和监控字段，不读日志正文。
- 每页3秒超时、发布5秒超时；每轮总30秒，扫描最多20秒/200页，页间50ms暂停；下一轮30秒后。
- 页中间汇总与游标同事务。完整桶发布时原子替换5m结果，以new-old差值修正小时/日汇总；崩溃重跑不重复累加。
- 与草案的多generation桶相比，首期采用上限2000组的短事务发布，避免增加版本表复杂度。超过预算会明确停留在旧快照并报告任务错误，不扩大事务或静默漏组。小时/日合并读取最多10000组。
- 初次处理、一小时后复核、次日最终复核，封存后推进连续finalized水位；不按最大ID猜测提交顺序。已封存区间不接受在线重建。
- 单来源四周期快照从最多1500行汇总一次读取生成；每轮最多64份。缓存64MiB/2000条，读快照并发4、singleflight、30秒TTL，数据库失败短暂退避。公共API不扫描logs。
- 管理员渠道表为当前来源最近24小时的小时粒度明细，最多2400行；与公共精确滚动摘要边界不同，接口不返回密钥或渠道配置。
- 5m/小时保留35天，日汇总90天；每轮最多删除500条旧汇总/任务。

单leader是数据库保护机制，不是无限吞吐保证。高基数超过2000组/桶或大量来源使快照积压时，需要观察lag并评估分片；不要通过加web副本提高聚合并发。

## API

沿用 `/api/model-plaza/metrics/all|detail|timeseries`，V2响应含schema_version=2。

- all返回按model_name/source_key区分的数组；详情和曲线要求source_key，只有唯一来源时可自动选择。旧channel_id链接解析来源后统计该来源所有渠道。
- detail支持period=1h/24h/7d/30d，顶部卡片与曲线同周期；返回as_of、partial、stale。请求未准备好返回preparing，不回退全来源统计。
- timeseries使用ETag与短缓存，detail含可选管理员数据，private/no-store。
- Root `GET /api/model-plaza/metrics/status`：覆盖、水位、lag、前20个待处理任务/错误。
- Root `POST /api/model-plaza/metrics/rebuild`，`{"bucket_start": UTC五分钟时间戳}`：仅排队未封存且仍在覆盖范围的桶，不在HTTP里扫日志。

## PostgreSQL迁移与开启

1. 默认 `MODEL_METRICS_V2_ENABLED=false`。先审核并在LOG_SQL_DSN指向的库执行 `scripts/migrations/2026-09-22-metrics-v2.pg.sql`。业务/日志同库则只执行一次。
2. 脚本包含logs可空新增列、V2小表和`CREATE INDEX CONCURRENTLY`部分索引；不能包裹总事务，不能由每个自动扩容节点同时执行。先检查长事务与锁窗口，脚本使用2秒lock_timeout。
3. 检查idx_logs_metrics_v2_scan的定义、indisvalid和indisready。worker在索引缺失/无效时拒绝扫描，避免线上全表扫描。启动不自动创建该大索引或V2表。
4. 所有节点统一新版本并配置 `MODEL_METRICS_V2_ENABLED=true`，保持 `MODEL_METRICS_ENABLED=true`、消费日志开启。V2替代旧worker；不要混跑旧版采集节点。
5. 从首个完整5分钟桶开始，不自动回填旧数据。30天曲线在覆盖不足时显示partial；逐步积累即可，无需等满30天才能使用。
6. 对照状态API、PG活动连接、WAL、autovacuum、锁等待和复制延迟观察。索引选择依据实际成本，可能选现有created_at索引；重点看有界扫描和页耗时。

自动扩容部署必须设置最大副本数与SQL_MAX_OPEN_CONNS/IDLE_CONNS，按PG总连接预算除以最大副本数及每副本池数计算。开启V2时未显式设置的默认值收敛到每池20个打开连接/5个空闲连接，显式环境配置仍优先；这不能代替整个集群的连接预算，也不假定已有PgBouncer兼容prepared statements。

## 清理、暂停与回退

已有V2状态表时，日志删除先持监控租约，再按原rankings租约/水位处理；删除截止取用户要求、两套连续封存水位的最小值。即使关闭V2开关仍保留水位保护。没有rankings时也采用500行短事务删除。

在线关闭监控/消费日志会持久化paused并撤销旧worker generation；恢复后新公开覆盖从完整桶重新开始，旧积压继续复核才能释放清理水位。暂停不代表允许清空未处理数据。

回退可关闭V2开关并部署兼容前端/旧worker；不删除新表或日志。旧统计依然是全来源汇总，回退期间不把它标成来源独立曲线。不要直接删除state解锁清理。

已加入来源隔离、异步写入、扣费失败、幂等重算、页回滚、失效租约、跨小时/空桶、30天混合分辨率、null/溢出、清理水位和HTTP无日志扫描测试。前端增加来源稳定身份测试。

本次已通过相关六个 Go 包回归、采集与聚合 race 测试、隔离工作树完整 build/vet、前端生产构建和11项目录测试。浏览器使用V2模拟响应验证Azure来源参数、1H卡片/曲线同步切换、null指标与390px无水平溢出，未出现pageerror；这不是线上真实数据端到端验证。

`scripts/verify-metrics-v2.pg.cjs` 使用隔离PGlite PostgreSQL引擎验证百万行数据上的generic plan、窄部分索引有效性和租约条件；高覆盖率数据可选旧时间索引，低覆盖率验证新部分索引。该环境不模拟生产多连接竞争、真正CONCURRENTLY索引或负载延迟，不能替代生产规格PG并发压测。脚本中的CONCURRENTLY仅为嵌入式验证移除，生产SQL保持不变。
