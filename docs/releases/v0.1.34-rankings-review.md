# v0.1.34 每日排行榜与数据库审查

## 审查结论与修复

本次审查针对排名功能，发现并修复以下问题后发布：

| 级别 | 问题 | 修复 |
| --- | --- | --- |
| P1 | 关闭榜单后旧清理路径可删除未统计日志，恢复时漏计 | 已初始化榜单的库始终保护统计水位 |
| P1 | 日志清理单个大事务可能长时间占用数据库及租约锁 | 每事务 500 行、单次最多 10000 行/5 秒，可继续调用 |
| P2 | 空闲节点每分钟创建冲突记录、写租约并释放 | 小表只读检查，有到期任务才竞争写租约 |
| P2 | 同一快照每分钟重复传输/解析完整 JSON | worker 使用持久 dirty 标记，节点同步在 SQL 中按版本过滤 |
| P2 | 常规时间索引查询仍需读取日志堆表 | 新增 PG 部分覆盖索引，固定 type 谓词以兼容 generic prepared plan |
| P2 | AWS Claude 经 OpenAI 兼容接口时漏计缓存输入 | 保留排名专用缓存字段，计费输入保持原值 |

## PostgreSQL 索引

```sql
CREATE INDEX IF NOT EXISTS idx_logs_ranking_daily ON logs (created_at)
INCLUDE (ranking_model_name, provider, ranking_tokens)
WHERE type = 2 AND ranking_tokens IS NOT NULL;
```

当前测试阶段数据少，按用户要求在版本中加入启动迁移。没有在开发过程中连接现有 PG 执行迁移。大表后续上线应提前用事务外 `CONCURRENTLY` 建同名索引。

## 实测边界

使用隔离的 PostgreSQL 引擎（PGlite/WASM）、10 万条模拟日志，包含错误和不可排名记录；执行 VACUUM ANALYZE 后强制 `plan_cache_mode=force_generic_plan`，查询固定一小时：

- 原时间索引：Index Scan，访问 105 个共享缓冲页。
- 新排名索引：Index Only Scan，访问 7 个共享缓冲页，Heap Fetches=0。
- 日志堆表约 130.2 MiB；新增排名索引约 4.2 MiB。仅包含约 7.5 万条可统计记录。
- 本地每批插入 5000 条的三次测量：原索引约 46/26/28ms；加覆盖索引约 80/64/46ms。模拟库基线仅含主键和时间索引，与业务日志表已有全部索引不完全一致；表明额外索引确实增加写入成本，不将 WASM 内存测试的时间或倍数作为生产容量指标。
- 生产环境 index-only scan 的回表次数取决于可见性映射和 autovacuum，刚写入的页可能仍需回表。

完整查询计划及测量数据保存在 `docs/reviews/2026-09-21-ranking-pg-plan.json`。不修改现有 ModelMetrics 监控的当前小时重扫逻辑；它的数据库开销仍独立存在。
